# Implement standardizing self-update on `go-selfupdate-lib`

Associated MADR: [0054-MADR-standardize-self-update-on-go-selfupdate-lib.md](0054-MADR-standardize-self-update-on-go-selfupdate-lib.md)

This PLAN has one phase, R1, which is documentation only. The MADR is `proposed`. R1 produces the
evidence report the owner asked for, so the MADR can be reviewed against the current library and
tree. The source phases the MADR's "Implementation Plan" note lists are **not** planned here. They
are added by a later amendment of this PLAN, after the MADR is accepted and the report reviewed.

## Goal

`docs/reports/0054-REPORT-go-selfupdate-lib-full-adoption-assessment.md` says exactly what full
adoption of `go-selfupdate-lib` requires. Full adoption moves self-update, release building and
publishing, service lifecycles, and installers out of `magic-cli-remote` and into the library. A
maintainer reading the report can review MADR 0054 without repeating the investigation.

## Scope

Only these files may change in R1:

* `docs/reports/0054-REPORT-go-selfupdate-lib-full-adoption-assessment.md` (new);
* `docs/README.md`, regenerated by `python3 scripts/check_records.py --write-index`. The table
  already carries owner rows for 0054 and 0182 that are not committed. Regeneration must keep
  them; the only intended additions are the rows for this PLAN and the new report;
* this PLAN, for the R1 execution record.

The MADR is the owner's uncommitted draft and is **not** edited in R1. Where the report finds that
one of the MADR's facts has changed, it says so and recommends the amendment. The owner decides
whether to make it.

## Implementation Steps

### R1 — Write and verify the full-adoption report

1. Record the baselines:
   * this repository's commit, Go floor, and current `mcplib` pin;
   * `go-selfupdate-lib`'s latest tag and peeled commit, Go floor, and dependencies.

   As observed on 2026-10-11, `v1.14.0` was published after the MADR, and `main` is two
   documentation commits past it.
2. Check every factual claim in the MADR against the current tree and library, and list the claims
   that have changed. Observed so far:
   * `v1.14.0` adds a `selfupdate/service/taskscheduler` backend, built on this repository's 0159
     measurements. That reopens the MADR's choice to keep the Windows adapter as product code.
   * 0159 D1, the Windows `setup-service --refresh`, has shipped (`refresh_schtasks.go`); only 0159
     P12 remains.
3. Give a file-level disposition for everything the self-update stack touches. Each item is
   deleted, shrunk, replaced by a library call, or kept as product code, with the reason. Cover:
   * `internal/updateclient`;
   * `cmd/mcremote` and `cmd/mcrelay` stamps;
   * the `internal/cli` and `internal/relay` version and update commands;
   * `internal/cli/service`, separating lifecycle control from definition rendering and setup;
   * the `Makefile` stamps;
   * `.github/workflows/ci.yml` release and publish jobs;
   * the `scripts/install*` scripts and their suites;
   * `scripts/verify-build-metadata.sh`.
4. Compare the hand-written installers' decided behaviors (0097, 0099, 0104, 0156, 0170) with the
   library's installer templates. Name every gap that blocks deleting the scripts.
5. List every change an operator or the phone can see: command streams and flags, the `version`
   string, the `/health` `version` field, installer options and exit codes, HealStart, and the
   new housekeeping files.
6. Recommend a phase order, the owner decisions each phase needs, and acceptance gates. Label each
   as a recommendation.
7. Regenerate the index. Read the complete report, this PLAN, and the generated index before
   concluding.
