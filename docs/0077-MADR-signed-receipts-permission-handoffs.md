## 0. Executive summary

**Question asked:** is it feasible, and worth doing, to produce cryptographically **signed receipts** for selected remote permission approvals and session "handoffs" — tamper-evident, non-repudiable proof of who authorized what and when?

**Finding, in one line: the hard part is already built for a different reason.** The phone already generates and durably holds a per-device P-256 keypair at pair time (ADR 0005), and the daemon already verifies possession of the matching private key on every connection. Reusing that same key to sign a receipt payload is a modest, well-scoped addition — not new PKI, not a new crypto dependency (Go: `crypto/ecdsa` stdlib; Dart: `pointycastle`/`basic_utils`, already vendored for the existing mTLS identity). **What's missing is plumbing, not cryptography**: the permission-resolution event today carries neither the chosen option nor the deviceID that answered it — both are computed, then discarded, on the current path (`internal/session/manager.go:1242-1255`).

**"Handoff" is a scope trap.** The phrase reads naturally as "transferring control of a session from one device/human to another," but **no such feature exists in this codebase** — `Manager.Authorize` (`internal/session/manager.go:768-799`) permanently and unconditionally rejects any device that isn't the session's first-touch owner. Signing a handoff receipt presumes a handoff mechanism to attach the signature to, and none exists. This MADR treats **permission-decision receipts** and **session-handoff receipts** as two separate proposals with very different feasibility, and recommends against building the latter until (if ever) an actual multi-device handoff feature is designed.

**Value:** real, but narrow. This is an enterprise/compliance/incident-forensics feature — proof for a security team that a specific human, not an auto-approve setting or a compromised phone, authorized a specific dangerous action. For the single-operator, personal-device model this product is built around today (ADR 0005 §Enrolment, README's "single operator-owned phone"), a signed receipt protects against a threat the current user mostly doesn't have (disputing their own past actions to themselves). It becomes valuable the moment a *second* party — an employer, a compliance auditor, a teammate reviewing what happened on a shared box — needs to trust the record without trusting the operator's word or an editable log file.

**Recommendation:** feasible and worth scoping as a real proposal for **permission-decision receipts** specifically (§7 gives a design sketch and the open questions that need answers before implementation). **Do not build "handoff receipts"** until a session-handoff feature itself is decided; if/when one is, revisit this MADR's §5.2.

**Amendment A1, pass 1 (2026-08-08 — same-day, post-acceptance):** the owner asked for deep research into prior art and for the design to be built as an extensible, canonical framework rather than a single-purpose "permission receipt" feature. §7.1 surveys the current (2026) landscape — in-toto/DSSE, SLSA, C2PA, AWS CloudTrail's log-integrity chain, and NIST's AI Agent Standards Initiative (identification / authorization / auditing / non-repudiation) — and §7.2 adapts the one idea that actually delivers "canonical and extensible": wrapping every receipt in an **in-toto-style typed `Statement`** (`subject` + `predicateType` + `predicate`) inside the already-locked JWS envelope, so a *second* receipt kind (session-handoff, or anything else later) is a new `predicateType` URI and predicate schema — never a change to the envelope, the verification code, or the storage layer. This is D5. §7.2 also explains why DSSE itself — the envelope that pattern comes from — is not adopted in place of JWS: on inspection it isn't more canonicalization-safe than JWS already is (both sign raw bytes, not re-parsed JSON), so swapping envelopes would have been churn for its own sake, not a real improvement. D3 stands.

**Amendment A1, pass 2 (2026-08-08 — same-day re-assessment):** asked to re-verify against codebase facts and "definitive" research and close remaining gaps. Every internal file:line citation in this document was re-read directly against the current tree (all confirmed accurate; one citation sharpened — §1's storage-truncation description). Every load-bearing external claim was re-fetched from its primary source (raw spec markdown, IETF RFC text, the publishing org's own page) rather than trusted from an earlier search-result summary — §7.1 marks each spot where that tightened something (most notably: the exact CloudTrail digest-chain field names, and independent confirmation that in-toto's own "human review" predicate proposal has sat open, unmerged, since 2021). The two previously-open questions (storage shape, signing-failure handling) are now locked as D6 and D8. A third pass over "what does D3 (JWS) actually cost" turned up D7: **JWS needs no external library on either side** once scoped to exactly ES256 Compact Serialization — both Go's classic `ecdsa.Sign` and Dart's `pointycastle` already expose the raw signature values JWS needs directly, verifiable against RFC 7515's own published ES256 test vector. This narrows D3's original "accepting a new dependency" framing without reversing the decision. **Result after this pass: D1–D8, zero remaining *open questions* — but a third, implementation-planning pass (same day) found two more facts worth locking before a PLAN could be called comprehensive: D9 (device public-key persistence) and D10 (the receipts matcher is new code, not reused code). See §7.2 D9–D10.**

## 1. Context

mcremote lets a phone remotely approve tool-execution permission requests from a coding agent — potentially destructive actions (`rm -rf`, force-push, prod deploy) run under the daemon operator's own account. Today, the only record that a specific decision happened is:

- An in-memory event bus and a bounded 800-event-per-session history ring (`historyBufferCap = 800`, `internal/session/manager.go:32`), which silently evicts old entries.
- A debounced, atomically-written JSON transcript per session (`m.scheduleHistoryPersist` → `Store.SaveHistory`, `internal/session/manager.go:1648-1662`, `internal/session/store.go:211-232`) — durable, but a flat file editable by anyone with the daemon's filesystem access (including the operator themself), not tamper-evident, and independently re-capped to the same 800-event budget on every write (`store.go:224-226`: `if len(events) > historyBufferCap { events = events[len(events)-historyBufferCap:] }`) — not merely inheriting an already-trimmed ring, the persisted file enforces its own ceiling. Whole-file read-modify-rewrite on every save is also, on its own, disqualifying for a tamper-evident log regardless of the cap: re-serializing the entire transcript on each write is exactly the operation that makes "was anything in the middle silently altered" unanswerable after the fact (relevant to D8, §7.2).
- `slog` diagnostic logging, which was never designed as an audit trail and doesn't capture permission decisions in structured form at all (verified: no `device_id`-stamped permission-decision log line exists anywhere in `internal/session` or the provider packages).

None of this is signed, none of it is tamper-evident, and — this is the concrete gap, not a vague one — **the record doesn't even say which device answered.** `RespondPermission` receives a `deviceID` parameter, uses it exactly once (the `Authorize` ownership gate), and never passes it further:

```go
// internal/session/manager.go:1242-1255
func (m *Manager) RespondPermission(ctx context.Context, sessionID, permissionID, optionID string, cancelled bool, deviceID string) error {
    if err := m.Authorize(sessionID, deviceID, true); err != nil {
        return err
    }
    sess, err := m.liveSession(sessionID)
    if err != nil {
        return err
    }
    ps, ok := sess.(provider.PermissionSession)
    if !ok {
        return fmt.Errorf("session %q does not support remote permissions", sessionID)
    }
    return ps.RespondPermission(ctx, permissionID, optionID, cancelled)
    //     ^ deviceID stops here — never reaches the provider or the event it emits
}
```

Every provider's resulting `permission_resolved` event (`internal/provider/acpagent/session.go:1291-1299`, `httpagent/session.go:697-701`, `opencode/http.go:1271-1275`, `kilo/session.go:509-513`, `codex/session.go:486-492,1001-1008`, `acphttp/session.go:760,816,1340` — goose's transport, structurally distinct from `httpagent` despite the similar name; missed in this MADR's original grounding and added during the implementation PLAN's test-coverage audit) carries only `PermissionID` and `Status` — not even the chosen `OptionID`, let alone who chose it. Confirmed directly against `internal/event/event.go`: the `Event` struct has **no `DeviceID` field at all**, anywhere, and the permission block (`event.go:445-447`) is `PermissionID` + `Options` only — the request's offered options, not the resolution's picked one.

So today, structurally, mcremote cannot even answer "which paired device approved this" after the fact, let alone prove it cryptographically.

## 2. What a receipt would need to prove, and what it can't

A useful signed receipt is a statement of the form: *"Device D, holding key K, asserts that at time T it chose option O for permission P in session S, where P concerned tool-call C."* For that statement to be trustworthy evidence:

1. **K must be bound to a specific human/device identity out-of-band**, and the daemon must independently know that binding — not trust the phone's self-report of it. ✅ Already true: `internal/auth/store.go:78-98` (`Device.ClientKeyFP`) binds a device record to a key fingerprint at pair time; `internal/ws/server.go:1169-1196` (`verifyClientKey`) checks possession of the matching private key on every connection, independent of anything the payload itself claims.
2. **The signed payload must describe the real action**, not the phone's account of it. This is the one place the current mTLS precedent doesn't transfer cleanly: TLS proves *possession of the key for this connection*; a receipt needs to prove *this key signed this specific decision content*. If the **phone** constructs the payload it signs (e.g., its own summary of the command), a compromised or buggy client could sign a payload that doesn't match what the daemon actually asked permission for. The safer construction is the daemon building the canonical payload (permission ID, session ID, the *exact* tool-call content it received from the provider, the option ID it's about to forward, a timestamp) and having the phone sign *that* — closer to a challenge-response than a self-attestation. This is a real design decision, not a detail (§7, open question Q1).
3. **The record must be durable and tamper-evident**, which a bounded ring buffer and an operator-editable JSON file are not. A receipt store is a small but new persistence surface (§7).
4. **Auto-approve answers must be structurally excluded.** They already are, incidentally: an armed auto-approve mode never emits `permission_request`/`permission_resolved` at all — it takes a separate code path (`noteAutoApproval`/`noteAutoApprovalItem`, `internal/provider/acpagent/session.go:1709-1750`) that produces `event.TypeApprovalSummary` cards, not permission events. A daemon self-answer therefore has nothing to attach a device signature to by construction — this is a genuinely convenient existing property, not something that needs to be built.

## 4. The two readings of "handoff"

**Reading A — permission/approval handoff.** The phrase describes what already happens every time a permission is answered: authority to let a dangerous action proceed is "handed off" from the pending-request state to a specific device's decision. Under this reading, "permission handoffs" and "session... handoffs" are the same event this MADR is really about, and the wording is just emphasizing that the receipt is *of* that handoff moment. This reading is **fully supported by existing machinery** per §3 and is what §5.1/§7 design against.

**Reading B — device-to-device session transfer.** A literal handoff: device A is controlling a live session, and control passes to device B (a different phone, a teammate, a shift change). **This feature does not exist.** `Authorize` doesn't have a code path for it; there is no revocation ceremony, no UI, no protocol message. Building "signed receipts for session handoffs" under this reading means first designing and shipping a handoff feature, then adding receipts to it — this MADR's scope is receipts, not session ownership transfer, so it can't respond to this reading without also proposing an unrelated, much larger feature. See §5.2 for the recommendation.

The nearest thing that exists today under Reading B is MADR 0068's connection replacement (`docs/protocol-v2.md:95-105`): a device's *own* older connection is closed (code `4001`) when it reconnects. This is not a handoff between two different approvers — it's the same identity reconnecting — so a "receipt" for it would only ever attest "this device replaced its own stale socket," which has no dispute value (nobody would ever contest that their own phone reconnected). Signing it would be cheap (the data already exists) but essentially valueless; not recommended.

## 5. Feasibility assessment

### 5.1 Permission-decision receipts (Reading A) — **feasible, moderate scope**

Everything in §3's "Exists" rows is real, verified infrastructure this can sit on. The work is:

1. Add `DeviceID` (new) and the chosen `OptionID` (currently absent) to the resolution path: `event.Event`, every provider's `RespondPermission`/resolution-emitting code (6 providers × ~1 call site each — acpagent, httpagent, opencode, kilo, codex, and acphttp/goose, the last of which was missed in this MADR's original grounding pass and only surfaced during the implementation PLAN's test-coverage audit; all structurally identical per §1's citations), and `session.Manager.RespondPermission`'s pass-through.
2. Decide and implement the signed-payload construction (§2 point 2 / §7.3 Q1) — daemon-constructed canonical Statement (§7.2, D5), phone signs it as a JWS, daemon verifies against the already-known enrolled public key.
3. A new durable receipt store — small, because only *selected* decisions get one (the user's own framing), not the full event stream. Append-only, backward hash-chained per D6/§7.2 (each Statement carries a top-level `chain.prev_sha256`, outside the type-specific `predicate`), the same shape as CloudTrail's digest chain (§7.1).
4. A verification path: something that can take a receipt and the device's public key and confirm the JWS signature over the Statement — could be a `mcremote receipts verify` CLI command in the existing style of `mcremote paths`/`mcremote engines`, or just documented as "any standard JWS verifier over this shape," keeping mcremote from needing to be the only tool that can check a receipt. Requires D9's public-key persistence to be in place first — today the daemon only ever retains a fingerprint, not a verifiable key.
5. Config surface for "selected" — D4 (config shape) + D10 (the actual matcher, new code, §7.2): a `receipts` section reusing `allow_rules`/`deny_rules`' naming convention, evaluated by a new mcremote-owned glob matcher — not, as D4 first assumed, a matching engine already implemented for grok (grok's rules are forwarded to its own CLI, never evaluated by mcremote).
6. A `predicateType` registry — even at v1 with exactly one receipt kind, define where/how `https://mcremote.dev/attestations/<kind>/v1` URIs get documented and versioned (a doc under `docs/`, mirroring how `docs/protocol-v1.md`/`protocol-v2.md` are the source of truth for wire messages), so the *next* receipt kind (D1's session-handoff follow-up, or anything else) has an obvious place to register itself without re-deriving §7.2's conventions from scratch.

None of this requires a new crypto library, a CA, hardware attestation, or a new transport. It is additive to the wire protocol (new fields, optionally a new message type) and additive to storage (a new small store, not a rework of the history ring).

### 5.2 Session-handoff receipts (Reading B) — **not feasible as scoped; own follow-up MADR (D1)**

There is nothing to sign yet. Building this means: (a) design a device-to-device session-transfer feature — who initiates, does the old owner consent or get overridden, what happens to a permission that's pending mid-transfer, how does `Authorize`'s current hard single-owner invariant get relaxed safely — then (b) add receipts to whatever that turns out to be. That's a materially larger MADR in its own right, unrelated in risk profile to §5.1. Per D1 (§4.1), this document does not shelve the idea indefinitely: the owner wants device-to-device handoff scoped as its own **near-term follow-up MADR**, independent of receipts. This document takes no position on that feature's design — once it exists, come back here to design the receipt layer on top of it using the same D2–D4 primitives (payload construction, JWS, scoping config) this MADR already locked for §5.1.

## 6. Value and benefit assessment

**Who benefits:** teams/operators who need to show a third party (employer, auditor, incident responder, teammate) that a specific human — not a misconfigured auto-approve, not an attacker who stole a bearer device token — authorized a specific dangerous action. This is fundamentally a **trust-with-a-third-party** feature. The threat it defeats — "I need to prove this to someone who doesn't just take my word for it" — doesn't really exist for a single person remote-controlling their own dev box, which is the model ADR 0005 explicitly designed for ("single operator-owned phone," `MADR-client-identity-decision.md`).

**What it's worth relative to the existing bearer-token/mTLS threat model:** genuinely additive, not redundant. Today's story is "the daemon accepted a WebSocket message from a client presenting the right cert" — good enough to gate *access*, but the resulting log of what happened is an editable JSON file the same operator's own account can rewrite. A signed receipt is meaningfully harder to fabricate after the fact than a log line, *given the same trust boundary the system already has* (ADR 0005 §"not hardware-bound/attestable" — a fully compromised phone can still forge receipts, exactly as a fully compromised phone can already impersonate the device today; this feature doesn't change that boundary, it strengthens what's provable *within* it).

**Where the value concentrates:**
- Incident forensics: "what did the agent actually do, and who said it was OK" after something breaks.
- Compliance / SOC2-style evidence: some orgs will specifically want cryptographic non-repudiation for actions taken by an AI agent against production systems, and today mcremote has literally nothing to offer here beyond "trust our logs."
- Deterrence: knowing a decision is signed and durable changes operator behavior even absent an actual dispute, the same way commit signing does.

**Where it doesn't help:** solo/hobbyist use, or any deployment where the same person controls both the phone and the daemon host and no one else will ever need to be convinced. For that majority of current usage (per the README's positioning), this is invisible overhead unless it's opt-in and cheap when unused — which the "selected" framing in the question already implies, and which §5.1's design (config-gated, small store, only for chosen patterns) delivers.

**Bottom line:** worth building as an **opt-in enterprise/compliance feature**, not worth building as a default-on behavior change. The engineering cost is real but bounded (§5.1) precisely because the hard cryptographic substrate is already sitting in the codebase for an unrelated reason (ADR 0005). That's the strongest argument for doing this now rather than never: the marginal cost is much lower than it would be if client identity had to be built from scratch to support it.

**External validation (Amendment A1, §7.1):** this isn't a speculative "some orgs might want it" — as of 2026-02-05, NIST's Center for AI Standards and Innovation is actively defining industry guidance around exactly four pillars for agentic systems (identification, authorization, auditing, non-repudiation, §7.1's table). mcremote already has the first two fully and the third partially; this MADR is concretely the fourth, and sharpens the third along the way (§7.2's tamper-evident storage). The value case here tracks a live, dated standards effort, not an assumption.

## 7. Prior art, canonical framework design, and open questions (Amendment A1)

### 7.1 Prior art — the 2026 signed-attestation and AI-agent-audit landscape

**Re-verified 2026-08-08 against primary sources, not summaries.** Every technical claim in this section was re-checked directly against the raw spec text (`raw.githubusercontent.com`, IETF datatracker, or the publishing org's own site) after the first research pass — flagged here because a couple of details tightened on the second look (noted inline).

**In-toto Attestation Framework + DSSE** ([spec](https://github.com/in-toto/attestation), [DSSE v1.0.2 protocol.md, raw](https://raw.githubusercontent.com/secure-systems-lab/dsse/v1.0.2/protocol.md)) is the closest prior art to what this MADR needs, and it comes from exactly the right problem class: signed statements about discrete events (a build step, a test run, a review), not auth tokens. It's a three-layer design:

1. **DSSE Envelope** (transport): `{payload: base64(body), payloadType: "<media type>", signatures: [{keyid, sig}]}`. The signature is computed over a **Pre-Authentication Encoding**, not the raw JSON — verbatim from the spec: `PAE(type, body) = "DSSEv1" + SP + LEN(type) + SP + type + SP + LEN(body) + SP + body`, `SP = ASCII space [0x20]`, `LEN(s) = ASCII decimal encoding of the byte length of s, with no leading zeros`. Supports multiple independent signatures over one payload natively.
2. **Statement** (header): `{_type: "https://in-toto.io/Statement/v1", subject: [{name, digest}], predicateType: "<URI>", predicate: {...}}` — field table confirmed verbatim against [statement.md, raw](https://raw.githubusercontent.com/in-toto/attestation/main/spec/v1/statement.md): `subject` is required, "MUST have `digest` set"; `predicateType` is required; `predicate` is optional, "MAY be omitted if `predicateType` fully describes the predicate." `subject` identifies what the statement is *about*, by content digest; `predicateType` is the extensibility hinge.
3. **Predicate** (body): an arbitrary, `predicateType`-specific schema. New attestation kinds are new predicate types — SLSA provenance and vulnerability-scan predicates are ratified this way. A proposed generic "human review" predicate ([in-toto/attestation#77](https://github.com/in-toto/attestation/issues/77)) has been **open, unmerged, since 2021-12-05** — nearly five years — which is itself informative: even in-toto's own maintainers have found a general-purpose "a human decided X" predicate harder to standardize than software-artifact predicates. That's a point *for* D5 owning its `predicateType` namespace outright (§7.2) rather than waiting on or depending on upstream ratification of a shape that may never land.

This is real, production infrastructure today, not a research paper: [GitHub Actions ships native SLSA provenance](https://docs.github.com/en/actions/concepts/security/artifact-attestations) (`actions/attest-build-provenance`), and [Python's package index has adopted the same attestation model](https://packaging.python.org/en/latest/specifications/index-hosted-attestations/) for PyPI. [SLSA](https://slsa.dev/spec/v0.1/provenance) itself is built on in-toto attestations end to end.

**COSE vs. JOSE/JWS** (RFC 9052 vs. RFC 7515): COSE is JOSE's CBOR/binary sibling — smaller wire size, no base64 overhead, used where JSON is a poor fit (WebAuthn, IoT). mcremote's entire protocol is JSON already (`docs/protocol-v1.md`), so COSE's compactness advantage is real but irrelevant here; adopting it would mean carrying two encodings for no benefit. Confirms staying in the JSON/JOSE family.

**JWS's own canonicalization story, confirmed directly against RFC 7515 §5.1** ([datatracker](https://datatracker.ietf.org/doc/html/rfc7515#section-5.1)): the JWS Signing Input is `ASCII(BASE64URL(UTF8(JWS Protected Header)) || '.' || BASE64URL(JWS Payload))` — the literal transmitted base64url bytes, never a re-parsed-and-re-serialized structure. Placed next to DSSE's PAE formula above, the two are doing the *same thing* (sign a deterministic byte encoding of the raw payload, not a canonical-JSON reconstruction of it) by different but equally sound means. This is the confirmation §7.2's "don't reopen D3" reasoning rests on — it isn't an inference from a summary, it's the two RFC/spec texts read side by side.

**AWS CloudTrail log file integrity validation**, exact digest-file field names confirmed against the [primary AWS doc](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-digest-file-structure.html): each digest file carries `previousDigestS3Object`, `previousDigestHashValue` + `previousDigestHashAlgorithm` (a hash of the *previous digest's content*), and `previousDigestSignature` (the *previous digest's own signature*, copied forward) — two separate references to the prior entry, not one. "The fact that each digest file contains a reference to its previous digest file enables a 'chaining' that permits validation tools... to detect if a digest file has been deleted," quoted directly from AWS's own "Digest file chaining" section. Validation starts at the newest digest and walks backward; a broken link identifies exactly where tampering (or deletion) occurred. §7.2's D8 simplifies this two-field chain into one field without losing the property it buys (explained there).

**Git commit signing over SSH** ([reference](https://blog.dbrgn.ch/2021/11/16/git-ssh-signatures/)) is a simpler, single-signer precedent worth naming for what it *doesn't* need: no CA, just an `allowed_signers` file mapping an identity to a raw public key — structurally identical to mcremote's own ADR 0005 "SSH `authorized_keys`, not PKI" model. Confirms mcremote is already following a proven minimal-infrastructure pattern for the underlying identity; this amendment only extends what that identity can attest to.

**C2PA Content Credentials** ([spec](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)) — the media-provenance standard — uses a parallel structure: a **manifest** contains **claims**, each claim contains **assertions** (individual provenance facts, including a standard "actions" assertion type for edits performed), and the whole manifest is signed via X.509. Another independent confirmation of the same shape: signed container → typed sub-statements, extensible by assertion/predicate type.

**W3C Verifiable Credentials** ([data model v2.0](https://www.w3.org/TR/vc-data-model-2.0/)) separates claims from proof similarly, but its issuer/holder/verifier three-party trust model and DID-based identity are built for cross-organization credential exchange — heavier machinery than a single daemon-and-its-own-paired-phones needs. Noted as prior art, not adopted.

**This exact problem, from 2026 AI-agent-governance research directly:** a [Zylos Research architecture note (2026-04-25)](https://zylos.ai/research/2026-04-25-agent-identity-provenance-signed-audit-trails/) on signed audit trails for autonomous agent tool calls explicitly recommends this shape for this exact problem class: *"in-toto's attestation framework and DSSE-style envelopes provide a practical shape: put the statement in a signed envelope, authenticate the payload type, avoid brittle canonicalization assumptions."* It also names, unprompted, the precise threat this MADR's D2 already defends against: an agent must not be able to "perform the action, [and] rewrite the journal" that's supposed to hold it accountable — i.e., the entity being granted permission must never be the one constructing or signing the record of that grant. mcremote's three-party shape already satisfies this: the coding-agent subprocess (untrusted, wants permission) is only ever the **subject** of a receipt; the daemon (orchestrator) **constructs** it; the phone (human) **signs** it. Worth stating plainly as a designed-in property, not an accident.

**Confirmed as a real, dated publication** by fetching the NIST page directly (not inferred from a search snippet): on 2026-02-05, NIST's National Cybersecurity Center of Excellence (NCCoE) published concept paper ["Accelerating the Adoption of Software and Artificial Intelligence Agent Identity and Authorization"](https://csrc.nist.gov/pubs/other/2026/02/05/accelerating-the-adoption-of-software-and-ai-agent/ipd) — **public comment closed 2026-04-02**, so as of this MADR's date the paper is past its draft-input stage, not still an open call. Its scope, quoted directly from the fetched page, is "identification, authorization, auditing and non-repudiation of AI agents, as well as controls to prevent and mitigate prompt injection techniques" — five focus areas; the first four are the ones this table maps (prompt-injection controls are out of scope for this MADR). Mapped against what exists in this codebase today:

| NIST pillar | mcremote today | Source |
| --- | --- | --- |
| Identification | ✅ Per-device P-256 identity (ADR 0005) | `client_identity.dart`, `internal/auth/store.go` |
| Authorization | ✅ Single-owner session claim (`Manager.Authorize`) | `internal/session/manager.go:768-799` |
| Auditing | ⚠️ Partial — durable but not tamper-evident (§1) | `Store.SaveHistory` |
| Non-repudiation | ❌ Missing entirely (§3) | this MADR |

This MADR is, concretely, the fourth pillar of a framework a standards body is actively formalizing for this exact problem class, on a live 2026 timeline.

**Independent convergent evidence, not just NIST framing it:** [airlock-protocol/airlock](https://github.com/airlock-protocol/airlock), a real open-source project, fetched and confirmed directly (not from search snippets) to implement "a signed, hash-chained receipt for every allow and every deny" for AI agent tool-call authorization, using Ed25519 `did:key` identities and SHA-256 hash-chained audit records — explicitly for regulator-facing compliance reporting. Its README **does not reference in-toto, DSSE, or SLSA at all** (confirmed by direct fetch) — it arrived at "signed + hash-chained decision receipts" independently, via OAuth/DID-based identity rather than in-toto's attestation shape. Two unrelated projects converging on the same core idea (sign the decision, chain the records) from different starting points is stronger evidence this is the right shape than either alone would be — and airlock's choice *not* to depend on in-toto/DSSE tooling is one more data point for this MADR's own H (§7.4): borrowing the useful pattern doesn't require adopting the upstream ecosystem's infrastructure.

### 7.2 The canonical, extensible framework: a typed Statement inside the existing JWS envelope (D5)

**The finding that actually answers "extensible and canonical":** it isn't the envelope (JWS vs. DSSE) — it's the **Statement/predicateType layering** in §7.1's in-toto model. That layer is what lets a whole ecosystem (SLSA provenance, vulnerability scans, human reviews, and whatever's proposed next) share one verification path. Nothing about it requires DSSE specifically; it's a payload-shape convention that fits equally well inside the JWS envelope D3 already locked. So D3 doesn't change — D5 adds the missing layer *inside* it.

**Why not switch the envelope to DSSE anyway, since that's where the pattern comes from?** Checked directly against the spec (§7.1): DSSE's headline property — signing a Pre-Authentication Encoding instead of raw JSON — is often described as solving "canonicalization," but JWS Compact Serialization already has the identical property: it signs `BASE64URL(header) || '.' || BASE64URL(payload)`, the literal transmitted bytes, never a re-parsed-and-re-serialized structure. Both formats sidestep JSON canonicalization ambiguity the same way, by never asking the verifier to reconstruct the signed bytes from parsed content. There is no real technical win from switching envelopes here — only churn against an already-locked decision (D3) and two ecosystems' worth of tooling to reconcile instead of one. DSSE is the right envelope to *point to* as prior art; it is not a reason to undo D3.

**The shape (D5).** Every receipt's JWS payload is a Statement. `chain` sits *outside* `predicate` deliberately (see D6 below) — it is the one field every receipt kind shares regardless of `predicateType`, so it belongs to the fixed wrapper, not to a per-kind schema that would otherwise have to remember to redeclare it:

```json
{
  "_type": "https://mcremote.dev/attestations/receipt/v1",
  "subject": [{
    "name": "session:3e0fce82-.../permission:per_a1b2",
    "digest": {"sha256": "<hash of the exact tool-call content the daemon received from the provider>"}
  }],
  "predicateType": "https://mcremote.dev/attestations/permission-decision/v1",
  "predicate": {
    "device_id": "dev_...",
    "option_id": "once",
    "decided_at": "2026-08-08T21:00:00Z",
    "tool_name": "bash",
    "detail": "rm -rf ./build"
  },
  "chain": {
    "scope": "device:dev_...",
    "prev_sha256": "<SHA-256 of the complete previous stored JWS compact string in this device's chain, or null for the first entry — D6>"
  }
}
```

(This is a deliberate, disclosed departure from strict in-toto Statement shape — a 5th top-level field, `chain` — not a claim of literal in-toto compatibility, consistent with §7.2's "pattern, not interop" framing above.)

- `_type` and the envelope/JWS mechanics never change across receipt kinds — every verifier mcremote ever ships only needs to understand *this* shape once.
- `predicateType` is versioned and owned by mcremote (`https://mcremote.dev/attestations/...`, not `https://in-toto.io/...` — this borrows the *pattern*, it does not claim in-toto/SLSA tooling interop, which would require adopting their exact predicate vocabulary too; not a goal here).
- A **second receipt kind is purely additive**: when the session-handoff follow-up MADR (D1) lands, it defines `predicateType: https://mcremote.dev/attestations/session-handoff/v1` with its own predicate fields — no change to the Statement wrapper, the JWS signing/verification code, the storage format, or the CLI verifier (§5.1 point 4). This is the concrete meaning of "framework, not a one-off feature."
- `subject.digest` binds the receipt to the *exact* tool-call content by hash, not by trusting a free-text summary to stay in sync — closing the same gap §2 point 2 already flagged, now with a standard field to put it in rather than an ad hoc one.

#### D6 — Storage: append-only, per-device, backward-chained (fully locked)

§7.1's CloudTrail precedent chains via two fields on the *next* entry (a hash of the previous entry's content, plus a copy of the previous entry's signature). mcremote's `chain.prev_sha256` collapses this to one field with an equivalent guarantee: **hashing the complete previous JWS compact string** (`header.payload.signature`, the exact bytes stored on the previous line) covers both the previous entry's content *and* its signature in a single SHA-256, since the signature bytes are part of what gets hashed. One field, not two, no loss of the property CloudTrail's two fields buy.

- **Chain scope: per device, not per session.** A session is transient; a device's accountability history is not — CloudTrail itself chains per-trail (a long-lived scope), not per-log-file (its transient unit), which is the same reasoning. "Show me everything device D approved, ever" is a materially more useful audit query than "show me everything approved in session S," and per-device scoping still answers the second question too (filter by `subject.name`'s session id within the one chain).
- **Location:** `<data_dir>/receipts/<device_id>.jsonl` — a new directory next to the existing `devices.json`/session dirs (`mcremote paths` → `data_dir`), one file per enrolled device.
- **Format: JSON Lines, one JWS compact string per line, strictly append-only.** This is a deliberate departure from `Store.SaveHistory`'s pattern (§1): that function reads the whole file, appends in memory, and rewrites the whole file on every save — correct for a transcript, **disqualifying for a tamper-evident log**, because a process that rewrites old bytes on every write cannot later prove it didn't also *alter* old bytes on some write. The receipts writer must open with `O_APPEND|O_CREATE`, write exactly one line, and never re-open for anything but appending or read-only verification.
- **Permissions:** `0600`, matching `devices.json`/`tls.key`'s existing convention (`internal/auth/store.go`, `internal/daemon/certs.go`).
- **Verification:** walk the file backward from the last line; for each entry, confirm the JWS signature against the device's enrolled public key (`Device.ClientKeyFP`'s corresponding cert) and confirm `chain.prev_sha256` matches the SHA-256 of the line above it. The first line in the file has `chain.prev_sha256: null`. A mismatch anywhere pinpoints the exact line tampering occurred at or after — CloudTrail's same backward-walk property (§7.1), now concretely specified for mcremote.

#### D7 — JWS implementation: hand-rolled ES256 Compact Serialization, no new dependency

§7.3 Q2 (previous pass) left "which JWS library" open, assuming one was needed on both sides. **Re-examined and resolved: no library is needed on either side**, once scoped to exactly what D3 actually requires — ES256, Compact Serialization, no JWE, no JWK discovery, no algorithm negotiation (mcremote fixes one algorithm and one key type forever, by design, the same minimalism ADR 0005 already commits to).

The one real gotcha, confirmed against [RFC 7518 §3.4](https://www.rfc-editor.org/rfc/rfc7518.html): JWS ES256 requires the signature as **raw, fixed-width `R || S` concatenation** (32 bytes each, big-endian, zero-padded, 64 bytes total) — *not* the ASN.1 DER `SEQUENCE{r, s}` encoding most general-purpose crypto APIs produce by default. Concretely, on each side:

- **Go:** the classic `ecdsa.Sign(rand, priv, hash) (r, s *big.Int, err error)` already returns `r` and `s` as separate values — *not* DER-wrapped (that's `ecdsa.SignASN1`, a different function). Left-pad each to 32 bytes and concatenate; no ASN.1 parsing required at all.
- **Dart:** `apps/mobile/lib/data/ws/client_identity.dart` already imports `pointycastle`; its `ECDSASigner.generateSignature` returns an `ECSignature` object exposing `.r`/`.s` as `BigInt` directly (the DER form is something the app's existing `X509Utils` code builds *from* those values for the client certificate — the raw values are already one layer up from that, not locked behind it). Same left-pad-and-concatenate step.
- **Verify against RFC 7515's own published test vector before shipping either side**: [Appendix A.3, "Example JWS Using ECDSA P-256 SHA-256"](https://datatracker.ietf.org/doc/html/rfc7515#appendix-A.3) gives a complete worked header/payload/signature example. A from-scratch ES256 Compact implementation should reproduce that exact appendix's output (or, since ECDSA signing is randomized, at minimum *verify* that published signature successfully) as a unit test before it signs a single real receipt — the standard, low-effort way to gain confidence in a hand-rolled serialization of a well-specified format, short of a full library.
- This resolves D3's original "accepting the cost of a JWS library" framing (§4.1) — that cost turns out not to exist at this scope. D3 (JWS as the format) still stands unchanged; only the "needs a library" assumption underneath it was wrong.
- If a library is ever preferred anyway (e.g. algorithm agility becomes a real requirement later): [`lestrrat-go/jwx`](https://github.com/lestrrat-go/jwx) v4 (2026) is the actively-maintained, comprehensive option on the Go side, confirmed via its own 2026 release notes. Not needed for v1; noted for completeness.

#### D8 — Signing round-trip: bounded, non-blocking, honest about gaps

§7.3 Q4 (previous pass) left the phone-signing failure/timeout path open. **Resolved:** the receipt-signing round trip (D2) must never be allowed to delay or fail the underlying permission grant — a compliance feature must not become a new hang vector for the core product. Concretely:

- The existing `PermissionTimeoutSeconds` fail-safe (already governing the human's yes/no decision, which can legitimately take a long time) is **untouched and unaffected** by receipts.
- The signing round trip gets its own **short, separate timeout — 10 seconds** — because signing itself is a local, near-instant cryptographic operation on a device that has already answered the permission, not a wait on human judgment; 10s generously covers phone wake/foreground latency without meaningfully delaying anything.
- On timeout (or a signature that fails verification on arrival), the daemon writes a marker entry to the chain — `predicateType: https://mcremote.dev/attestations/receipt-unavailable/v1`, `predicate: {reason: "timeout"|"invalid_signature", permission_id, device_id}` — rather than silently omitting the line. A gap in an append-only chain with no explanation is indistinguishable from tampering; a marker entry keeps the chain's backward walk (D6) unbroken and tells a later auditor exactly what happened instead of leaving them to guess.
- **Refined during implementation planning:** an unsigned entry doesn't fit D6's "every stored line is a verifiable JWS compact string" format — and JWS's own `alg: none` (RFC 7515 §6) is a well-known anti-pattern, not a clean way to get one. Resolved: **the daemon signs the marker itself**, using the ECDSA P-256 private key backing its own TLS serving certificate (`certs.Bundle.Certificate.PrivateKey`, already generated and held by every running daemon — `internal/certs/certs.go:239`, same curve D7's signer already handles). This is a weaker attestation than a device-signed receipt ("the daemon says signing failed," not "a human decided X") and is never confused with one: `predicateType` alone tells a verifier which key to check against — the device's enrolled key (D9) for `permission-decision`, the daemon's own serving key for `receipt-unavailable`. No new trust anchor: the phone already pins the daemon's serving-cert fingerprint at pair time (`mcremote pair code --qr`'s printed `Cert: sha256:…`).

#### D9 — A gap the first two passes missed: the daemon doesn't persist the device's public key, only its fingerprint

Found during the implementation-planning grounding pass (2026-08-08, third pass), not the two research passes above — recorded here because it's load-bearing for whether D6's "verify later, offline" property actually works.

Confirmed directly: `internal/ws/server.go:500` computes `c.clientKeyFP = certs.SPKIFingerprint(r.TLS.PeerCertificates[0])` — a **SHA-256 hash** (`internal/certs/certs.go:549-552`: `sha256.Sum256(cert.RawSubjectPublicKeyInfo)`) — and only that hash string is ever passed to `Store.CreateWithClientKey(name, clientKeyFP string)` (`internal/auth/store.go:269`) for persistence. `Device`/`deviceRecord` (`internal/auth/store.go:78-99`) have no field for the actual public key, anywhere. This is not an oversight in the existing system — it's *correct* for what the existing system needs: TLS itself cryptographically verifies possession of the private key at handshake time, live, every connection; the daemon only ever needs to compare "does this connection's fingerprint match the enrolled one," and a fingerprint is sufficient for that. **A fingerprint cannot verify a signature, though** — that needs the actual public key, and D6 explicitly requires verification to work *later*, *offline*, by a party (an auditor, `mcremote receipts verify`) with no live connection to the device in question. This is a genuinely new requirement receipts introduce; the gap was invisible before because nothing before this needed it.

**Resolved:**

- **What to persist:** `cert.RawSubjectPublicKeyInfo` — the exact same DER bytes already being hashed into `ClientKeyFP` today, not the whole certificate (no CN, no validity window — consistent with ADR 0005's "identity is the key, not the cert"). New field `ClientKeySPKI []byte` (base64 in JSON) alongside `ClientKeyFP` in both `Device` and `deviceRecord` (`internal/auth/store.go`).
- **New devices (post-this-change):** captured at the exact point the fingerprint already is — `server.go:500` also sets `c.clientKeySPKI = r.TLS.PeerCertificates[0].RawSubjectPublicKeyInfo`, threaded into `CreateWithClientKey` alongside the fingerprint.
- **Already-enrolled devices (pre-this-change):** **no forced re-pair.** Self-healing backfill: `verifyClientKey` (`internal/ws/server.go:1169-1196`) already runs on every authenticated connection and already confirms `c.clientKeyFP == dev.ClientKeyFP` before proceeding — at that exact point, if `dev.ClientKeySPKI` is empty, the daemon persists the currently-presented `c.clientKeySPKI` (safe: the fingerprint match just proved this connection's key *is* the enrolled one). A device that never reconnects after this ships simply can't have its historical receipts verified until it does — a documented, honest limitation, not a silent one, and not worth blocking this MADR over: it self-resolves the next time each existing device connects, with zero user action.
- This is additive, backward-compatible storage (a new optional field, `omitempty`) — no migration script, no version bump, no forced action.

#### D10 — The receipt pattern matcher is new code, not reused code

D4 (§4.1) originally framed "selected" scoping as reusing `allow_rules`/`deny_rules`' *matching*. Checked directly against the code that consumes them (`internal/provider/grok/grok.go:138-141`): each rule is forwarded verbatim as a `--allow <rule>`/`--deny <rule>` argv flag to the `grok` binary — **grok's own process interprets the rule**, mcremote's Go code never evaluates it. There is nothing to generalize; a receipts matcher has to be written from scratch, because unlike grok's rules (which gate whether the *agent* auto-proceeds), a receipts rule gates whether *mcremote itself* decides to trigger the signing round trip — a decision mcremote must make locally, before anything reaches the provider.

**Resolved:**

- **Matching semantics: shell-glob syntax** (`*`, `?`, `[...]`) — the same well-understood mental model as `.gitignore`, no new runtime dependency, no regex-injection surface to worry about. **Corrected during implementation (PLAN P5):** the natural first reach, Go stdlib `path.Match`, was tried and found broken for this exact use case — its `*` refuses to cross a `/` (path-separator-aware glob semantics, correct for one path segment, wrong here), and `detail` is very often a file path. Verified directly: `path.Match("*rm -rf*", "bash rm -rf ./build")` — this MADR's own worked example two lines below — returns `(false, nil)`: no error, just a silent non-match, exactly the failure mode an operator would never notice until wondering why a receipt never showed up. Fixed by translating the glob to a `regexp` internally (still Go stdlib, still no new dependency); the operator-facing syntax (`*`, `?`, `[set]`) is unchanged.
- **Matched against:** `tool_name + " " + detail` (e.g. `"bash rm -rf ./build"`) — the same human-readable summary already carried on the `permission_request` event (§3's "rich enough" row), not a new field.
- **Config shape** (new top-level `receipts` section, cross-provider — D4's naming convention, now correctly scoped as config-only): `enabled bool`, `allow_patterns []string`, `deny_patterns []string` (renamed from `allow_rules`/`deny_rules` in the locked design specifically *because* these are glob patterns evaluated by mcremote, not passthrough CLI rules like grok's — reusing the exact same field name for two different semantics across two config sections would be a footgun, not a convenience). Deny takes precedence over allow when both match, matching the conservative default most permission-adjacent config in this codebase already uses.
- **Where this runs:** in the daemon, immediately after `RespondPermission` succeeds (§7.2 D8's non-blocking round trip already establishes this timing) — never inside a provider, keeping the decision provider-agnostic as D4 intended.

### 7.3 Resolved and open questions

All five are now resolved — nothing left open for the PLAN to invent from scratch; only implementation-level details (exact Go/Dart code structure, test layout) remain, which is what a PLAN is for.

**Q1 — Who constructs the signed payload, phone or daemon? Resolved by D2: daemon constructs, phone signs.** Reinforced by §7.1's Zylos citation: the entity requesting a dangerous action must never be the one who can also manufacture proof that it was approved. **Message names, locked:** `permission.receipt_request` (daemon→phone, carries the unsigned Statement) and `permission.receipt` (phone→daemon, carries the signed JWS back) — matching the existing dot-separated, verb-suffixed naming convention already in use for `permission.respond`/`question.respond` (`internal/protocol/messages.go`).

**Q2 — Signature/envelope format. Resolved by D3 (unchanged) + D5 (typed Statement) + D7 (no library needed).** JWS ES256 Compact Serialization, hand-implemented on both sides per D7's exact recipe, verified against RFC 7515 Appendix A.3 before shipping.

**Q3 — Storage shape. Fully locked by D6.** `<data_dir>/receipts/<device_id>.jsonl`, append-only, `0600`, backward-chained via `chain.prev_sha256`. Exact path, format, and the append-only-vs-`SaveHistory` distinction are all specified in §7.2 D6 — nothing left for the PLAN to decide here beyond writing the code.

**Q4 — Signing failure/timeout. Fully locked by D8.** 10-second bounded timeout on the signing round trip only, fully decoupled from `PermissionTimeoutSeconds`, explicit `receipt-unavailable` marker entry on failure so the chain never has an unexplained gap.

**Q5 — "Selected" config surface. Resolved by D4 (config shape) + D10 (the actual new matcher)**: a `receipts` section with `allow_patterns`/`deny_patterns` glob rules (shell-glob syntax, regexp-backed — see D10's implementation correction above, not Go `path.Match`), evaluated by mcremote itself against `tool_name + " " + detail`, so an operator can say "commands matching `*rm -rf*`, `*push --force*`, or `*kubectl delete*` get a signed receipt" without paying the cost on every routine permission ask.

### 7.4 Alternatives considered

| Alternative | Verdict | Why |
| --- | --- | --- |
| **A. Client-signed receipts on the existing mTLS keypair, JWS-wrapped (hand-rolled, no library — D7), in-toto-style typed Statement payload (D5)** (this proposal, D2–D8) | Accepted | Reuses ADR 0005 infrastructure for the underlying key/algorithm; JWS gives standard-wire-format interoperability (D3) at **zero new-dependency cost** once D7 showed the library assumption was wrong; the Statement/predicateType layer (D5) is what makes it a framework rather than a point feature, also at zero envelope cost |
| B. Daemon-signed-only attestation (no phone signature) | Reject as primary | Proves "the daemon received a message," not "a specific human decided" — no non-repudiation gain over a well-formatted log; could be a *cheap add-on* alongside A (both sign, neither alone can forge — DSSE/JWS-JSON-Serialization both support multiple signers over one payload if this is ever wanted) but not a substitute |
| C. Hardware-attested keys (Android Keystore/StrongBox, iOS Secure Enclave) | Defer | Strictly stronger, but ADR 0005 explicitly declined this complexity for the base identity system; scoping it in just for receipts is new, platform-specific work — a future hardening MADR, not v1 |
| D. External timestamping/notarization service | Reject | No external dependency is needed for this threat model; adds an availability dependency for no proportionate benefit |
| E. Structured durable logging, unsigned | Cheaper fallback, not equivalent | Solves "the record disappeared" but not "the record could have been edited by the same operator it's meant to constrain" — doesn't deliver non-repudiation, which is the actual ask |
| F. Bespoke ECDSA + fixed JSON shape, not JWS | Considered, not chosen | Once D7 established both options need the same hand-rolled implementation effort (no library either way), the tie-breaker is interoperability: JWS is a wire-format any external tool already knows how to verify; an mcremote-invented shape is not. No offsetting benefit to going bespoke once the "library cost" argument for it evaporates |
| G. **(A1)** Swap the envelope to DSSE instead of JWS | Considered, not chosen | The origin of the Statement pattern, but per §7.2 offers no real technical advantage over the already-locked JWS (both sign raw transmitted bytes); adopting D5's Statement shape gets the actual benefit without reopening D3 |
| H. **(A1)** Full in-toto/Sigstore ecosystem adoption (Rekor transparency log, Fulcio keyless signing, cosign tooling) | Reject | That tooling solves *ephemeral/anonymous build-identity* signing via OIDC — a different problem than mcremote's, which already has long-lived enrolled device keys (ADR 0005). Borrowing the Statement *shape* (D5) captures the useful part without the unneeded infrastructure |

## 8. Risks

| Risk | Note |
| --- | --- |
| Compromised phone forges consistent-looking receipts | Inherent to the existing trust model (ADR 0005); not a new weakness introduced by this feature, but worth stating plainly so the feature isn't oversold as attack-proof |
| Payload-construction mismatch (Q1) if built carelessly | A phone-authored summary that can drift from the real tool-call content would make the receipt attest to the wrong thing — this is the one place a naive implementation could look done while proving nothing useful |
| Feature scope creep into "session handoff" (Reading B) | Addressed directly in §4/§5.2 — recommend explicitly descoping until a transfer feature exists |
| Storage growth | Bounded by the "selected" config surface (Q5) — not every permission, so growth is operator-controlled |
| False sense of compliance completeness | A receipt proves *this system's* record of a decision; it doesn't replace an org's broader audit program. Worth a line in any user-facing docs if built |
| **(A1)** Mistaking "in-toto-inspired" for "in-toto-compatible" | §7.2's `predicateType` URIs live under `https://mcremote.dev/...`, not `https://in-toto.io/...` — a receipt won't validate against generic in-toto/SLSA tooling out of the box, and docs/marketing must not imply it does. The value taken from that ecosystem is the *shape*, not interop; worth being explicit about this the first time it's documented user-facing |
| **(A1)** `predicateType` sprawl over time | The whole point of D5 is that new receipt kinds are cheap to add — which also means nothing stops them from multiplying without a real need. §5.1 point 6's registry doc is the guardrail: every new `predicateType` gets written down in one place before it ships, the same discipline `docs/protocol-v1.md` already applies to wire messages |
| **(A1, re-assessment)** Hand-rolled ES256 signing (D7) gets the byte format wrong | The `R\|\|S` vs. ASN.1 DER distinction (§7.2 D7) is well-documented but easy to miss if D7's guidance isn't followed exactly — a wrong-format signature fails *every* verification, silently and permanently, for every receipt signed that way until caught. Mitigated by D7's own requirement: reproduce/verify RFC 7515 Appendix A.3's published test vector before the PLAN's implementation ships, on both the Go and Dart sides independently |
| **(A1, re-assessment)** Per-device chain (D6) never rotates or bounds | An enrolled device that's never revoked accumulates one never-truncated `.jsonl` file for its whole lifetime — correct per D6's "receipts are for selected, infrequent, high-stakes decisions" framing (§5.1 point 5's config gate keeps volume low), but worth a documented note in the PLAN that chain length is *unbounded by design* (truncating it would defeat D6's entire purpose) and that this is a feature, not an oversight, so nobody "fixes" it into a ring buffer later and quietly reintroduces §1's original problem |

## 9. Recommendation — accepted 2026-08-08; Amendment A1 finalized same day

**Permission-decision receipts (§5.1): accepted**, D1–D10 locked (§4.1, §7.2) — **every open question this MADR raised is now resolved**; nothing remains for a PLAN to design, only to build. Feasible on existing infrastructure at every layer checked: identity and key (ADR 0005, D2, D9 — including the offline-verification gap D9 closes), wire format (D3/D5/D7 — no new dependency after all), storage (D6 — exact path, format, chain scope), scoping (D10 — the actual matcher, corrected from D4's original "reuse" assumption), and failure handling (D8 — bounded, non-blocking, honest about gaps). Engineering cost is concentrated entirely in plumbing (device ID + chosen option through to the event/storage layer, the daemon→phone round trip's two new message types) and in careful-but-well-specified implementation (D7's signature format, verified against a published RFC test vector) — not in open design decisions, cryptography, or new infrastructure. Opt-in and config-gated (D4), not a default-on behavior change, matching the "selected" framing in the original question.

**The framework property, concretely:** D5's in-toto-style typed Statement plus D6's device-scoped, kind-agnostic `chain` wrapper mean a *second* receipt kind — starting with session-handoff once D1's follow-up MADR defines what that even is — is a new `predicateType` URI and a new predicate schema. Nothing else changes: not the envelope, not the signing code (D7), not the storage format or file layout (D6), not the failure-handling logic (D8), not the verification path. That is the literal, load-bearing meaning of "framework, not a one-off feature" this amendment was asked to deliver.

**Session-handoff receipts (§5.2): not scoped by this MADR, but not shelved either (D1).** A device-to-device session-transfer feature needs its own MADR first — there is currently nothing for a signature to attach to. Once that follow-up MADR lands, come back here and design its receipt layer as a new `predicateType` (D5) reusing D2–D8 unchanged.

Next step: a PLAN document that implements D1–D10 as written — skeleton (event/proto fields for D2) → device public-key persistence (D9) → JWS+Statement signing code (D5/D7, test-vector-verified) → storage (D6) → the pattern matcher (D10) → daemon↔phone round trip (D2's `permission.receipt_request`/`permission.receipt`) → failure handling (D8) → CLI verification surface (§5.1 point 4) → `predicateType` registry doc (§5.1 point 6) → live tests, phased similarly to prior provider/security MADRs in this repo. Separately: scope the device-to-device session-transfer MADR per D1.
